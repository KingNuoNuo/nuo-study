# 客户端设计

孩子端 = 平板横屏，家长端 = 手机竖屏。这不是「一个 App 两种角色」，而是**两个形态差异很大的应用**。

## 1. 双端形态对比

| | 孩子端 | 家长端 |
|---|---|---|
| 设备 | 平板 10–12 寸，横屏 | 手机，竖屏 |
| 主界面形态 | 三栏并排（导航 / 题面 / 作答） | 单列纵向堆叠 |
| 核心动作 | 作答、手写、录音 | 拍照、确认、看报告 |
| 需要权限 | 麦克风、（可选）相机 | 相机、相册、通知 |
| 网络特征 | 长时间离线作答 | 短时在线，上传为主 |
| 更新策略 | **极谨慎**（孩子正在做题） | 灵活 |
| 防分心 | 必须（时长锁、切出提醒） | 不需要 |

**结论：两个 application module**

```
:app-student          孩子端（平板横屏，独立图标/清单/Application）
:app-parent           家长端（手机竖屏，相机权限）
:core-ui              设计系统、通用组件
:core-network         Retrofit + OkHttp + kotlinx.serialization
:core-data            仓储层 + Room（孩子端缓存）
:core-sync            WorkManager 同步队列
:feature-homework     今日作业        （双端复用，布局分支）
:feature-capture      截图上传 + 识别确认（仅家长端）
:feature-chinese      语文            （仅孩子端）
:feature-math         数学            （仅孩子端）
:feature-english      英语            （仅孩子端）
:feature-report       学情报告        （仅家长端）
```

为什么用两个 application module 而不是 productFlavor：

- 孩子端**绝不能在孩子做题时被更新覆盖**（`android:autoUpdateMode` 与更新提示策略不同）
- 两端权限清单不同，家长端要相机，孩子端不要去要相机权限
- 两端 `minSdk` 可能不同（家里的旧平板可能是 Android 8/9）
- 独立打包，可以只给孩子装孩子端

## 2. 导航结构：作业与学习分离

顶层是两个平级板块，**左右滑动切换**：

```
┌──────────┬──────────┐
│   作业    │   学习    │   ← 顶层 HorizontalPager：可滑动、也可点击
└──────────┴──────────┘
      │           │
      │           └─ 学习内部：语文 / 数学 / 英语  ← 顶部标签，仅点击
      └─ 作业：老师布置的任务单
```

| | 作业 | 学习 |
|---|---|---|
| 内容来源 | 家长上传截图 → 识别 → 确认 | 题库按知识点 / 错题推荐 |
| 数据模型 | `assignment` + `assignment_item` | `practice_session` |
| 有无截止 / 提交 | 有 | 无，随时练 |
| 作答记录落在 | `answer_record.assignment_item_id` | `answer_record.practice_session_id` |

**两条来源在数据层分离，但作答记录统一落 `answer_record`** —— 学情分析只读这一张表，
不做 UNION。表上加了 CHECK 约束保证一次作答有且仅有一个来源（已实测生效）。

### 三条滑动规则（每条都是踩过的坑）

1. **滑动不能是唯一入口。** 顶部必须有可见的「作业 | 学习」指示器，点击也能切。
   只靠手势会让功能不可发现，也不满足无障碍要求。
2. **作答中必须锁定滑动。** 手写画布和 Pager 的手势会打架 —— 孩子写竖式时横向一滑就翻页，
   草稿直接丢掉。规则：进入某个作业项的作答态后 `userScrollEnabled = false`，
   退回列表才恢复。
3. **不要做嵌套横向 Pager。** 学习内部若也用横向滑动，内外两层会抢手势（Compose 经典坑，
   需要写复杂的嵌套滚动仲裁）。学习内部用顶部 Tab **点击**切换即可 ——
   切换成本极低，不值得为手势去写仲裁逻辑。

### 顺带解决的一个产品问题

这个结构让**「学习」不依赖家长**：孩子想做几道口算，不必等家长拍作业、确认、发布，
打开学习板块直接练。这是把两者分开的主要产品理由，也顺带把「孩子自主使用」这条路径
从「家长必须参与」里解放出来。

## 3. ⚠️ 本项目有两套 SQLite，职责完全不同

这是最容易搞混、也最容易埋雷的地方，先钉死：

| | 服务端库 | 孩子端本地库 | 家长端本地库 |
|---|---|---|---|
| 位置 | 家庭后端 `data/app.db` | 平板内部 Room | 手机内部 Room |
| 角色 | **主库，唯一事实来源** | **缓存 + 待同步队列** | 图片缓存、草稿暂存 |
| 谁定义 | `db/schema.sql`（手写 DDL） | Room `@Entity` 注解生成 | 同左 |
| 结构关系 | 17 张表，完整业务模型 | **不是主库的 1:1 拷贝**，只存需要的 | 极简，可只用文件缓存 |
| 可否重建 | ❌ 必须备份 | ✅ 随时清空重建 | ✅ 随时清空重建 |

**孩子端 Room 只建这 6 张表就够了**（不要照着服务端 18 张抄）：

| 表 | 作用 |
|---|---|
| `local_assignment` | 当日 + 近 7 日的作业单 |
| `local_item` | 作业项 + 题干 + `answer_mode` |
| `local_practice` | 进行中的自主学习会话与题目（学习板块离线可用） |
| `answer_outbox` | **待同步队列**：clientReqId / 来源(作业或练习) / payload / retryCount / state |
| `local_media` | 录音、手写图的本地文件路径 |
| `local_kp` | 知识点树（离线展示弱项用） |

`answer_outbox` 一张表服务两条来源，用字段区分即可 —— 同步逻辑不需要写两套。

## 4. 孩子端横屏布局规则

- **强制横屏**：`android:screenOrientation="sensorLandscape"`
- **三栏**：左侧导航 `200dp` / 中间题面 `flex` / 右侧作答 `300dp`
- **最低适配** 1024×768；推荐 1280×800 以上
- 题干最小 **20sp**，正文 16sp（护眼 + 桌面距离）
- 触控目标 ≥ **48dp**
- 作答区宽度按学科切换，不做统一

### 各学科作答方式映射（对应 `assignment_item.answer_mode`）

| 学科 | 作业形态 | answer_mode | 说明 |
|---|---|---|---|
| 语文 | 古诗默写 | 手写(2) | 方格纸背景，横屏下写竖排更方便 |
| 语文 | 阅读理解 | 键盘(1) | 长文本，需键盘 + 手写批注 |
| 语文 | 习作 500 字 | 键盘(1) | 字数实时统计 |
| 数学 | 口算 / 分数计算 | 键盘(1) | **自绘数字键盘**，不要弹系统键盘 |
| 数学 | 竖式计算 | 手写(2) | 横屏给了足够横向空间写竖式 |
| 数学 | 几何 / 作图 | 手写(2) | 需圆规直尺工具条 |
| 数学 | 应用题 | 键盘+手写 | 列式键盘，过程用手写 |
| 英语 | 单词拼写 | 键盘(1) | 自绘英文键盘（避免自动纠错/联想） |
| 英语 | 跟读 | 录音(3) | 显示波形 + 评分 |
| 英语 | 听力 | 键盘(1) | 音频播放器 + 选项 |
| 通用 | 朗读 / 背诵 | 录音(3) | 打卡类 |
| 通用 | 手抄报 / 实践 | 拍照(4) | 打卡类 |

> **自绘键盘是必须的**：系统键盘的自动纠错和联想会替孩子拼出正确答案，
> 英语单词拼写和数学口算都会失去意义。

### 手写实现要点

- Compose `pointerInput` + `Canvas`，按 `MotionEvent` 的 `pressure` 做压感笔迹
- 笔迹先落本地文件（大量 Path 对象放内存会 OOM），只把缩略图给 Compose 渲染
- 提交时**上传图片**而非笔迹矢量数据 —— 批改端只需要看到字

## 5. 防分心（不做设备所有者 Kiosk）

孩子平板通常还装了游戏，但**不建议做真 Kiosk**（需要 ADB 或 DPC，家庭场景过重）。

按成本从低到高：

1. **系统「屏幕固定」**：家长手动开启，零代码，够用
2. **App 内切出检测**：`onPause`/`onStop` 记录离开时长，超过阈值回来后提示
3. **时长锁**：累计使用到 `student.daily_limit_min` 弹锁定页，需要家长端确认才能继续

## 6. 家长端手机布局（竖屏，单列）

```
┌────────────────────┐
│ 孩子切换 · 100% 小满 │  ← 顶栏：孩子切换 + 今日完成度
├────────────────────┤
│                    │
│   [ 拍照录入作业 ]   │  ← 主 CTA，占屏 1/3，唯一的大按钮
│                    │
├────────────────────┤
│ 历史作业        ⟳ 刷新│  ← 2026-10-09 新增，见下
│  待确认 · 孩子看不到  │
│   · 数学 10月9日  [✎][🗑]│
│  已发布              │
│   · 英语 10月8日  [✎][🗑]│
├────────────────────┤
│ 今日完成 3/8   →     │
│ 本周学情报告  →      │  ← 学习数据入口
│ 设置                │
└────────────────────┘
```

家长端的设计原则：**主路径只有三步——拍、确认、看**。不要把学生端的功能塞进来。

### 历史作业模块（2026-10-09）

挂在录入页最下方，**刻意不做成第四个底部 Tab** —— 它是补救入口，不是一等功能。

解决两个原先无路可走的情况：

1. 日期选错 / 标题打错 / 漏了一项 → 唯一出路是「删了重录」，而删除入口根本不存在；
2. 识别跑完但没点确认就退出 App → 那条草稿失联（列表看不到、孩子端也看不到），
   只能重拍同一张图（还会命中识别缓存）。

设计要点：

- **分「待确认 / 已发布」两组**，不混排。草稿是待办（孩子看不到，事情没完），
  已发布是档案；混排会让家长以为草稿已经生效。
- 点击整行进编辑页（**整页，不是底部弹层**：一条语文卷子能拆十几项，
  弹层里键盘一弹只剩两行可视区）。编辑页可改日期 / 标题 / 是否需提交 /
  作业项增删改；草稿多一个「发布」按钮。
- **科目不可改**：它与日期构成作业单身份键，改它等于换一条单子，硬做只会撞唯一键。
- 删除必须过二次确认弹窗 —— 服务端是**硬删除**（无回收站），这个弹窗是唯一的误删防线。
- 保存后**不会自动同步到孩子端**，界面上必须写明「孩子端下次刷新才会更新」，
  否则家长会以为没保存成功然后反复点。

由于家长在横屏截图，**上传前必须做裁剪引导**（把老师那几条消息框出来），
否则识别质量会被群聊里的无关内容拖垮。

## 7. 离线与同步策略

| 方向 | 策略 |
|---|---|
| 拉取 | 进入首页拉「当日 + 近 7 日」作业；家长确认发布后孩子端下次同步可见 |
| 推送 | `answer_outbox` 由 WorkManager 排空，指数退避（首次 10s，上限 30min） |
| 幂等 | 每条作答带 `clientReqId`（UUID v4），服务端唯一索引兜底 |
| 冲突 | 以服务端为准；本地只保证「不丢」，不保证「最新」 |
| 媒体 | 先落本地文件，再传；传完才允许清理本地副本 |
| **删除对齐** | 拉取时顺手删掉「服务端已不存在的已发布作业单」，**只在本次一定拉全了的日期区间内**做（见下） |

⚠️ **拉取是 upsert，不自带删除**。家长删掉一条已发布的，孩子端会一直显示它
（直到 `purgeOld` 按日期扫掉，那是 30 天后）。所以 `AssignmentRepository.refresh()`
拉完要补一次对齐，判据是：

- 返回条数 `< LIMIT` → 服务端把符合条件的一次给全了，区间取 `assignDate >= 最旧一天`；
- 返回条数 `== LIMIT` → 最旧那天可能被截断，区间收紧成 `assignDate > 最旧一天`；
- 返回**空列表** → 什么都不删（分不清「真没有」还是「这次没拉到」）。

删完再清一次 `local_item` 里的孤儿项（Room 不会替你级联）。

**「提交」按钮的语义是「本地已保存」，不是「已上传」。** 断网时按钮反馈必须是
「已保存到平板，联网后自动上交」，不是报错。
