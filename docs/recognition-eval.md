## 二、踩到的三个坑（都会让链路静默失效）

### 坑 1：思考过程会吃光 token，返回空的正文

这是最危险的一个——**HTTP 200，不是报错，但 `content` 是空字符串**。
第一次跑图 1（英语，2 天 7 项）时：

```
finish_reason = length
completion_tokens = 8000      ← 全部用满
reasoning_tokens  = 8000      ← 全部是思考
content           = ""        ← 正文一个字没有
```

服务端把推理链放在**独立的 `reasoning` 字段**（好事：不污染 JSON），
但它和正文**共享同一个 `max_tokens` 预算**。预算给少了，思考写满就截断，正文永远出不来。

**处置**：`max_tokens` 提到 `32000`（该模型最大输出 65536，安全），并关闭思考。

### 坑 2：只有 `reasoning_effort="none"` 关得掉思考

同一张图、同一问题、各加一个参数，实测：

| 参数 | reasoning_tokens | 是否生效 |
|---|---|---|
| （不加） | 430 | — |
| `reasoning_effort: "none"` | **0** | ✅ 生效，耗时 2.1s |
| `thinking: {"type":"disabled"}` | **0** | ✅ 生效，耗时 1.5s |
| `enable_thinking: false` | 608 | ❌ **静默忽略** |
| `reasoning_effort: "low"` | 777 | ❌ **静默忽略**（只有 `none` 关得掉） |

**后两个不报错、不改行为**——这类「参数被静默吞掉」是排查成本最高的故障。

### 坑 3：会撞 429 限流

第一次全量跑时图 3 直接失败：

```
HTTP 429 {"message":"inference exceeds tpm/rpm limit","type":"rate_limit_error"}
```

**处置**：链路已内置指数退避重试（429 → 10s/20s，最多 3 次）。
另外注意**开了思考后单次调用要 50s+**，加上限流，生产链路必须有重试，不能裸调。

## 三、A/B：关闭思考 vs 开启思考

| 指标 | 关闭思考 | 开启思考 |
|---|---|---|
| 图 1（2 天 7 项） | 28.9s / 1020 tok ✅ | 52.6s / 7303 tok ✅ |
| 图 2（QQ 语文） | 6.0s / 584 tok ✅ | **180s 超时 ❌** |
| 图 3（QQ 数学） | 17.1s / 670 tok ✅ | **180s 超时 ❌** |
| 成功率 | **3/3** | 1/3 |
| token 总量 | 12,341 | — |

**质量差异（很小的一个）**：开启思考时，图 1 第 2 项被拆得更规范——

- 关思考：`title = "在家坚持默写巩固英语书上学过的内容，每天不少于15分钟，可以是单词，词组，句子，课文，书上的笔记常看常记"`
- 开思考：`title = "在家坚持默写巩固英语书上学过的内容"` + `requirement = "每天不少于15分钟，可以是单词，词组，句子，课文，书上的笔记常看常记"`

后者才是提示词要求的形态（题干与附加要求分离）。

**决策**：**默认关闭思考**。代价是题干/要求偶尔合并，可以在家长确认界面上让人工拆
（一次点击的成本远低于等 3 分钟）。若后续想同时拿到质量与速度，正确做法是
**两段式**：关思考跑全量，只对 `confidence < 0.7` 的项开思考复跑——而不是全程开思考。

### 几个真正体现设计价值的观察

1. **「星期几」当校验位，日期不再靠猜。**
   图 1 只有「星期四 10月8日」没有年份，模型回填的依据是：
   `图中「星期四 10月8日」，2026-10-08 确为星期四`。图 2 只有「昨天 14:43」，
   模型换算出 2026-10-08 并在 `needs_review` 里主动提示「日期由相对时间推算，请核对」——
   **这正是设计里要的行为：不确定的日期必须让家长看见。**

2. **噪声真的被拦住了。**
   图 2 里「【反馈】作业🌹：40、19、10、3、28…」是一串**学号**，不是作业。
   模型把它放进 `not_homework`（kind=反馈），作业项里只有「大册 单元练习二」。
   如果这里失手，孩子的作业单上会出现 18 个数字项。同一张图里的
   「智慧校园缴费」截图也被正确识别为与作业无关。

3. **练习册照片没有被逐题转录。**
   图 3 老师附了一整页计算题照片。模型只登记 `attachments`（3 条，`transcribe: false`），
   没有把 12 道竖式题转成 12 个作业项。提示词里那条禁令是有效的——
   **这条如果不写，模型会非常积极地把整页题目抄一遍。**

4. **截图被截断时它会说。**
   图 1 第 4 项在图片底部被截断（「每个单词和标…」），模型照抄可见部分并在
   `needs_review` 里明确报告「原文不完整，请核对」。**承认看不见**比猜一个结尾重要得多。

## 六、落库验证（这才是对数据模型的实战检验）

识别结果**真的灌进了 `db/schema.sql` 建出来的库**，不是只解析出 JSON 就完事：

```
assignment         4 行   全部 status=0（草稿，待家长确认）；已发布 0 行
assignment_item   11 行
capture            3 行
recognition_cache  3 行（hit_count=1）
recognition_job    6 行
```

`family` 单行约束、`answer_mode` 的 `CHECK (0..4)`、外键、时间戳格式全部在真实写入中生效。

### 顺带暴露的两个缺口（已补）

1. **`assignment` 缺 `need_submit`。** 图 1 两张作业单都标着「**无需提交**」，
   而模型**判对了**（`need_submit=False`）。但原 DDL 没地方存这个字段，
   孩子端就无法区分「要做」和「要做且要交」。→ 已加 `need_submit INTEGER NOT NULL DEFAULT 1`。
2. **`answer_mode` 缺 `0=无需作答`。** 「每天默写不少于15分钟」这类过程性要求，
   App 内不需要任何作答动作。→ 已加枚举 `0` 与 `CHECK (answer_mode BETWEEN 0 AND 4)`。

### 自己代码里的一个 bug（已修，值得记下来）

第一次跑完后重跑同一批图，作业项**翻了一倍**（3 项 → 6 项，全库 11 → 22）。
原因：`assignment` 上有 `ON CONFLICT (student_id, assign_date, title) DO NOTHING`，
但作业项是**无条件重插**的。

→ 修法：落库前判断作业单状态。`status=0`（草稿）则先删旧项再插（重识别应当覆盖）；
`status>=1`（已发布）**一律不覆盖**，转人工修正流程。
修完实测：连跑两次，`assignment_item` 恒为 11 行。

> 教训：**幂等不能只在最外层做。** 父表的 `DO NOTHING` 保护不了子表。

## 七、还没覆盖的风险（下一步该测的）

| 风险 | 为什么危险 | 怎么测 |
|---|---|---|
| **纸质照片**（家长拍练习册，非 App 截图） | 透视畸变、光照不均、手写批注遮挡印刷体 | 拿手机真的拍几张，别用截图 |
| **歪斜 / 阴影 / 多页拼接** | 版面分析失败会导致整页漏读 | 同上 |
| **语文作文类作业** | 无法结构化，只能落打卡卡 | 找一次作文作业的截图 |
| **一张图里两位老师、多科混排** | 拆错科目 → 学情数据全串 | 已覆盖一半（图 2 有语文+数学，但数学那条被截断） |
| **识别正确但孩子看不懂** | 老师原话有大量省略与黑话（「大册」「课课练」） | 需要家长确认界面补「白话解释」，这属于 M2 |

**建议**：先补 10–20 张自己拍的纸质照片跑一遍。截图是**最简单**的输入，
它全对只能说明「可以做」，不能说明「够用」。
